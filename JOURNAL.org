* 🔬 How =doom/reload= works — and where it stops
Source: =~/.config/emacs/lisp/lib/config.el:76= (Doom =59cdaa32=, 2026-10-02).

1. =require=s all incremental packages, then runs =doom sync -B -e= in a
   compilation buffer (=doom-reload-command=).
2. On success, inside =(with-doom-context 'reload …)=: runs
   =doom-before-reload-hook=, calls =general-auto-unbind-keys=, re-runs
   =startup--load-user-init-file=, then =doom-after-reload-hook=.

*What it can't do* (why a restart is sometimes unavoidable):
- *Nothing is ever unloaded.* Removed packages, hooks, advice, timers, and
  minor modes keep running until a restart.
- =defvar= / =defcustom= never re-initialise an already-bound variable.
- =use-package :config= of an already-loaded feature only re-runs if the
  form is re-evaluated (=after!= on a loaded feature runs immediately).
  Mostly fine, but state accumulates (duplicate hook entries, double advice).
- Native-compiled =.eln= of changed packages stays mapped in memory.
- Doom's own docstring: /"save yourself the headache and simply run 'doom
  sync' outside of Emacs and restart. That will always work."/

*How we work around it:* your =lisp/+*.el= are live symlinks into this repo
(not Nix store copies), so for those files a plain =load-file= is enough,
with no reload or rebuild. =config.el=, =init.el=, and =packages.el= are
Nix-store links: they need =nrs=, then =doom sync=, then reload/restart.
I'll only ask you to restart the daemon when one of the limits above
actually applies, and I'll say which one.
